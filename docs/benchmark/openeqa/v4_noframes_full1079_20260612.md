# OpenEQA v4 — no-default-frames, evidence fetched via keyframe CLI, 2026-06-12

First full-set OpenEQA run on the **no-default-frames** pipeline. The QA turn now
attaches **zero** seed frames: the agent starts blind and **fetches every piece
of visual evidence itself** through the OpenEQA CLI tools (`keyframe_selector`,
`view_frame`, `view_bev`, `list_objects`). This is the architecture the user
asked for after v3 — "不输入任何默认帧, 而是在 guide prompt中提示 codex 可以通过
cli 调用我们的 keyframe 获取视觉信息". Same full **ScanNet split — 1,079 questions
across all 89 local scenes**.

## Headline

**MNAS = 64.09** over all 1,079 ScanNet questions. **Completion 1,079/1,079
(100 %)**, 0 unresolved failures, 0 empty predictions, `num_frames=0` on every
sample (confirming no seed frames). Prompt-cache hit rate 0.976 (mean cache ratio
0.466).

| Category | n | MNAS |
|---|---:|---:|
| object state recognition | 162 | 77.01 |
| attribute recognition | 163 | 70.55 |
| object localization | 160 | 67.50 |
| functional reasoning | 146 | 66.78 |
| world knowledge | 141 | 63.12 |

Judge-score histogram (1–5): `1:249  2:22  3:156  4:176  5:476` (44.1 % perfect
matches; 23.1 % complete misses). Compared to v3 the distribution shifted toward
the floor: complete misses rose 14.4 % → 23.1 % and perfect matches fell 54.6 %
→ 44.1 %.

## The headline number: v4 (no frames) vs v3 (8 seed frames + tools)

Dropping the 8 uniform seed frames cost **−9.87 MNAS overall** on the identical
1,079-question split, same answerer, same judge. This is the decision-grade
tools-vs-seeded A/B that v1–v3 never had (matched fold, matched judge, only the
seed-frame input changed).

| Category | v3 (8 frames + tools) | v4 (no frames, tools only) | Δ |
|---|---:|---:|---:|
| object recognition | 70.51 | 53.21 | **−17.31** |
| attribute recognition | 82.67 | 70.55 | **−12.12** |
| object state recognition | 86.88 | 77.01 | −9.88 |
| spatial understanding | 58.61 | 49.17 | −9.44 |
| object localization | 76.88 | 67.50 | −9.38 |
| world knowledge | 70.74 | 63.12 | −7.62 |
| functional reasoning | 69.35 | 66.78 | −2.57 |
| **Overall** | **73.96** | **64.09** | **−9.87** |

Interpretation: the categories that lean hardest on *seeing the right view
immediately* — object recognition (−17.3) and attribute recognition (−12.1) —
regressed the most. With no seed frames the agent must first localize the
relevant object via `keyframe_selector` before it can read off a label or an
attribute; when retrieval surfaces the wrong/insufficient view, or the turn runs
out of tool budget first (see below), the answer degrades. Functional reasoning
(−2.6) barely moved — it depends more on scene-level priors than on a specific
pixel-perfect frame. **This is an expected cost of the cleaner architecture**:
v4 removes the uniform-sampling crutch and makes the agent own 100 % of its
evidence, at a ~10-point MNAS price on this judge.

## Tool-budget pressure (new in v4)

Because the agent must gather *all* evidence itself, tool usage is much heavier
than v3:

- **90 / 1,079 questions (8.3 %)** hit the `max_tool_calls=24` ceiling and were
  finalized from the evidence gathered in 24 actions (vs essentially 0 in v3,
  which started with 8 frames in hand).
- **Per-turn latency** jumped accordingly: min 3.7 s / p50 **114.2 s** / p90
  230.7 s / p99 332.8 s / max 502.1 s; mean 123.9 s. v3's p50 was 14.6 s — an
  ~8× increase per question, all of it tool-loop time.
- **133 finalization re-asks** (turn produced no usable final_response on the
  first finalize and was re-asked once).

The 8.3 % budget-ceiling rate is the most actionable lever: raising
`max_tool_calls` (or improving first-shot keyframe retrieval so fewer tool calls
are needed) is the obvious next experiment to claw back some of the −9.87.

## Scope (why 1,079 and not 1,636)

Unchanged from v3. `open-eqa-v0.json` has 1,636 questions: 1,079 `scannet-v0` +
557 `hm3d-v0`. Only the prepared **ScanNet** assets are present locally
(`data/OpenEQA/scannet/`, 89 scenes); there are **no hm3d assets**.
`filter_questions_with_local_scenes` drops the 557 hm3d questions automatically,
so "full" = the complete ScanNet split (all 89 scenes, all 1,079 questions).

Reproduce the headline from the DB:

SELECT round(avg(mnas), 2) AS mnas, count(*) AS n
FROM samples
WHERE run_id = 'v4_noframes_full1079_20260612' AND judge_score IS NOT NULL;

The matched v3-vs-v4 per-category delta (the headline A/B):

```sql
SELECT v4.category,
       round(v3.m, 2) AS v3_mnas, round(v4.m, 2) AS v4_mnas,
       round(v4.m - v3.m, 2) AS delta
FROM (SELECT category, avg(mnas) m FROM samples
      WHERE run_id='v4_noframes_full1079_20260612' GROUP BY category) v4
JOIN (SELECT category, avg(mnas) m FROM samples
      WHERE run_id='v3_tools_full1079_20260612' GROUP BY category) v3
  USING (category)
ORDER BY delta;
```

## What changed vs v3

- **Code:** the no-default-frames redesign (`bfb00c2`). `OpenEqaQuestionAnsweringTask`
  now takes only `(question, scene_dir)`, sets `image_paths=()`, and the rules
  prompt mandates tool-based evidence gathering. `OpenEqaFrame` /
  `DEFAULT_NUM_FRAMES` / `uniform_frame_ids` / `select_frame_ids` /
  `prepare_frames` were removed from `scene.py`; `--num-frames`, `--max-image-size`,
  `--skill-path`, `--tools` were removed from the CLI; default sandbox is now
  `workspace_write` + network.
- **Run config:** 20 workers (v3 used 30 + a recovery pass).
- **Everything else identical:** same 1,079 ScanNet split, same `gpt-5.4`
  answerer, same `gemini-2.5-pro` judge, same loop caps (24 / 4).

## Caveats (read before citing)

- **This is a real regression vs v3 on this judge: −9.87 MNAS.** It is the
  *cost* of removing seed frames, not a bug. v4 is the honest baseline for the
  no-frames architecture; v3's 73.96 is only reachable by re-adding uniform seed
  frames, which the project has decided against.
- **Judge mismatch.** We judge with `gemini-2.5-pro`; the OpenEQA paper uses
  GPT-4. MNAS is judge-sensitive — **64.09 is not directly comparable to
  published OpenEQA leaderboard numbers.**
- **ScanNet only.** The 557 hm3d questions are excluded (no local assets).
- **Tool-budget ceiling is binding for 8.3 % of questions.** Those 90 questions
  were finalized early at `max_tool_calls=24`; their scores are a floor, not the
  agent's ceiling. Raising the budget is an untested lever.
- **BEV is a schematic** (no `mesh.ply`): top-down floor plan from ConceptGraph
  object footprints + camera trajectory, not a textured-mesh raster.
- **Data is local-only.** `data/open-eqa-v0.json` + `data/OpenEQA/scannet/` are
  gitignored symlinks; they never arrive via `git clone`.

## Next steps

1. **Tool-budget sweep.** Re-run with `max_tool_calls` ∈ {32, 48} to measure how
   much of the −9.87 is budget-bound vs retrieval-quality-bound (8.3 % of
   questions are currently truncated at 24).
2. **First-shot keyframe quality.** Inspect the 249 score-1 questions (esp.
   object/attribute recognition) to see whether `keyframe_selector` surfaced the
   wrong view or the agent reasoned poorly over a correct one.
3. **Design the canonical OpenEQA pilot fold** (stratify on the 7 categories,
   salt-lock against this v4 full-set baseline) for cheap, comparable ablations —
   so the budget sweep above is a fold run, not another 2.4 h full pass.
4. **Per-call traces** so `tool_calls` / `llm_calls` populate and we can attribute
   the −17.3 object-recognition drop to specific tool-loop failure modes.
5. **hm3d split** once those scenes are prepared, for the full 1,636-question MNAS.
