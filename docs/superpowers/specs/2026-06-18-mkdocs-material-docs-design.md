# MkDocs Material Documentation Design

Date: 2026-06-18

## Goal

Use MkDocs Material as a human-readable web layer over the existing Markdown
files under `docs/`. The Markdown files remain the single source of truth:
agents continue to read the same `.md` files directly, while humans browse the
rendered site.

## Scope

In scope:

- Add MkDocs Material configuration for the repository.
- Organize only `docs/` content into chapters.
- Add lightweight index pages that explain how to read each section.
- Preserve existing benchmark records, engineering notes, assets, and SQLite
  files in place.

Out of scope:

- Do not include top-level `README.md`, `AGENTS.md`, or `CLAUDE.md` in the
  MkDocs navigation.
- Do not rewrite existing document bodies.
- Do not move benchmark assets or rename historical version documents.
- Do not introduce a second documentation source or generated Markdown copy.

## Proposed Information Architecture

The documentation site will use this chapter model:

```text
docs/
├── index.md
├── python_code_agent_quality_guide.md
├── codex_agent/
│   ├── index.md
│   ├── nr3d_tools_plan_20260609.md
│   ├── view_image_adapter_fix_20260609.md
│   ├── prompt_caching_20260608.md
│   ├── reasoning_summary_and_effort_20260610.md
│   ├── reasoning_carryover_caching_ak_routing_20260611.md
│   └── skill_loop_and_reasoning_dropped_20260609.md
└── benchmark/
    ├── index.md
    ├── nr3d/
    │   ├── README.md
    │   └── v*.md
    └── openeqa/
        ├── README.md
        └── v*.md
```

The chapter order should be:

1. Documentation home.
2. Development standards.
3. Codex Agent engineering notes.
4. Benchmark archive.

Within benchmark chapters, keep each existing `README.md` as that benchmark's
timeline page and link every dated version record beneath it.

## MkDocs Configuration

Add a root-level `mkdocs.yml` with:

- `site_name` set to a project-specific title.
- `docs_dir: docs`.
- `theme.name: material`.
- A hand-written `nav` so the chapter order stays stable.
- Markdown extensions for code blocks, admonitions, tables, table of contents,
  and collapsible details.
- `strict: true` if the current documents build cleanly; otherwise defer strict
  mode until existing historical links are fixed.

MkDocs configuration is allowed at the repository root because it is tooling
metadata, not a second documentation content source.

## Index Pages

Add three lightweight index pages:

- `docs/index.md`: site entry point and reading route.
- `docs/codex_agent/index.md`: summary of engineering-note themes.
- `docs/benchmark/index.md`: benchmark archive overview and links to NR3D and
  OpenEQA timelines.

These pages should summarize and route; they should not duplicate benchmark
results or long technical content already present in the historical records.

## Dependency Management

Prefer adding `mkdocs-material` to the existing development dependency group in
`pyproject.toml`, so local setup remains:

```bash
uv pip install -e ".[dev]"
mkdocs serve
```

If adding the dependency is not desired, document the one-off install command
instead. The recommended path is to add it to dev dependencies because this is a
repo-level documentation tool.

## Verification

After implementation, verify with:

```bash
mkdocs build
```

If dependencies are added to `pyproject.toml`, also run the repository's normal
Python checks only if Python source files are touched. For a docs-only MkDocs
configuration change, `mkdocs build` is the relevant verification gate.

## Risks

- Existing Markdown may contain links to historical files that are not present
  in the current checkout. If strict mode fails on those links, build without
  strict mode first and leave link cleanup as a separate task.
- Large assets and `runs.sqlite` should not be copied or regenerated by the
  docs setup. They remain repository assets linked from Markdown.
- Navigation can become stale when new benchmark records are added. Keep the
  nav explicit for readability, and update it whenever a new dated benchmark
  doc is committed.
